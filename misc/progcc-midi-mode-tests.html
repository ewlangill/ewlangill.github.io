ProGCC Midi Mode tests

Turning controller input into musical control.

I’m developing an experimental native USB-MIDI mode for ProGCC 3.2. The aim is to use the controller’s buttons, sticks and gyro to play and shape sound over its USB cable, with editable mappings and profiles. Runtime MIDI is handled by the firmware; the design does not need a computer-side translator.

Built and tested in software. Hardware validation is still ahead.

The candidate firmware has not been installed on my controller. The results below come from source inspection, firmware builds and host tests using simulated hardware boundaries. They do not establish native MIDI enumeration, audible performance, latency, compatibility or saved settings surviving a real power cycle.

What’s implemented

The candidate adds a separate power-on-selectable MIDI mode, four mapping profiles, button note/CC actions, four stick axes and three gyro axes, with channel, CC and pitch assignments. It includes recenter/clutch handling, bounded output rates and note-release cleanup. Existing controller modes, settings and recovery paths are being preserved; their behavior with the new firmware still needs physical verification.

A local browser editor can read the current bank, edit mappings, apply changes temporarily and export a bank file. The firmware handles performance after the editor closes. Temporary Apply and permanent Save are separate operations.

A pitch-bend starting point

Profile 2 maps left-stick X to pitch bend on MIDI channel 1, with A sending note 60 at velocity 100 on the same channel. The intended receiver setting is ±12 semitones: two octaves from one end of the stick to the other. The receiver must be set deliberately; the controller does not automatically send an RPN pitch-range change.

Software checks cover sending a due bend before a same-channel Note On and keeping note releases independent of bend rate limits. This is an editable preset, with musical feel and physical stick response still to be tested.

Save and readback tests

The firmware’s explicit Save operation snapshots the bank already applied to the controller. It first releases musical output and waits for cleanup and USB transmission to drain. It then makes one guarded storage attempt and verifies the full written sector. Retrying the retained transaction returns the cached result instead of writing again.

The browser Save client is implemented and host-tested. It compares the expected bank with the applied bank before sending Save, waits for a final result and compares readback afterward. It never applies an editor draft as part of saving. The visible Save button and its complete editor workflow are still next.

  • A mismatched draft sends no Save request.
  • A dropped final acknowledgment retries the same transaction with one writer attempt.
  • A modeled restart restores the saved Profile 2 after a different temporary bank was applied.
  • A storage failure is cached, and the earlier saved bank remains available in the RAM model.
  • Busy, Unsupported, Canceled and disconnect responses are handled. A missing reply leaves the outcome unknown; reading RAM alone cannot confirm storage.

The C/JavaScript checks pass with address and undefined-behavior sanitizers. Separate backend tests cover 4,097 interrupted-write prefixes in simulated flash. Tests around the pinned TinyUSB MIDI class cover queued data, transfers in flight, the terminating zero-length packet and transfer failures. These are useful software checks, not evidence of real flash behavior or USB performance.[1]

Build checkpoint

The save-enabled Release candidate uses 426,984 bytes of flash and 125,852 bytes of main RAM. The disabled comparison build uses 402,080 and 118,796 bytes respectively. Static checks retain the 3,880-byte settings structure and all 23 existing descriptor arrays. This does not prove runtime memory headroom or gameplay behavior.

Next tests

Next are the deliberate Save interface, physical stick and gyro calibration, mode indication and recovery preparation. Before an installation trial, I still need to establish the exact installed firmware and layout, make private backups and verify a bounded update and restoration procedure. Native MIDI enumeration, actual saved power cycles and physical musical performance remain unverified.

This post shares the development results. There is no firmware download or installer here.
